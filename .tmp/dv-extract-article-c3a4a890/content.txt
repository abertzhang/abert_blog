[html:l15] Flutter 渲染管线：从 Widget 到 Layer 的完整链路
[html:l17] 作者 abert
[html:l18] ·
[html:l19] 2026-08-12
[html:l20] ·
[html:l21] Flutter
[html:l22] ·
[html:l23] 约 9 分钟阅读
[html:l25] 很多人对 Flutter 的性能印象来自一句话：Widget 很轻，重建不贵。这句话是对的，但它只覆盖了整条链路的第一段。真正决定一次更新要花多少时间的，往往是你没有显式写过的那几层。
[html:l27] 一次更新经历了什么
[html:l29] 从调用 setState 到屏幕上出现新像素，中间至少经过四个阶段：构建（Build）、布局（Layout）、绘制（Paint）与合成（Composite）。每个阶段都有自己的失效范围，理解这个范围，才能判断代价落在哪里。
[html:l31] dart
[html:l32] class ArticleListView extends ConsumerWidget {
[html:l33] const ArticleListView({super.key});
[html:l35] @override
[html:l36] Widget build(BuildContext context, WidgetRef ref) {
[html:l37] final articles = ref.watch(articleListProvider);
[html:l38] return articles.when(
[html:l39] data: (items) => ListView.builder(
[html:l40] itemCount: items.length,
[html:l41] itemBuilder: (context, index) => ArticleTile(article: items[index]),
[html:l42] ),
[html:l43] loading: () => const Center(child: CircularProgressIndicator()),
[html:l44] error: (error, stack) => ErrorView(error: error),
[html:l45] );
[html:l46] }
[html:l47] }
[html:l49] 上面这段代码本身没有问题，但 ref.watch 的位置决定了整棵子树的失效范围：把订阅放在列表项之外，任何一条数据变化都会重建整个列表容器。
[html:l51] 为什么代价常常不在 setState
[html:l53] 构建阶段的成本通常是可控的，因为 Widget 只是不可变的配置对象。真正昂贵的是布局与绘制：它们要处理真实的几何信息与像素。
[html:l55] 布局阶段的真实开销
[html:l57] 当一棵子树的约束发生变化，布局会沿着这棵子树自顶向下重新计算。常见的放大器有三个：
[html:l59] 在滚动容器里使用无界高度的布局组件，导致每帧重新测量；
[html:l60] 把频繁变化的状态订阅放在靠近根节点的位置，放大失效范围；
[html:l61] 在同一帧里连续触发多次状态更新，却没有合并成一次。
[html:l63] 判断性能问题的最快方式，不是读代码找可疑点，而是先让 DevTools 告诉你时间花在哪个阶段，再回到代码里找对应的那行。
[html:l65] 把结论变成可执行的检查
[html:l67] 把上面的分析整理成一套可以在每次提交前跑一遍的动作：
[html:l69] shell
[html:l70] flutter run --profile --trace-startup
[html:l71] flutter build apk --split-debug-info=build/symbols
[html:l73] 如果时间线里布局与绘制占比明显高于构建，说明问题在几何而非状态；反之则应优先检查订阅粒度与状态合并。两种情况的优化方向完全不同，先分清楚再动手，能省掉大量无效重构。
